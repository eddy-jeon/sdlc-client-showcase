Why we built it

사람이 외워야 할 것을
줄이기 위해 만들었습니다.

AI가 강력해질수록 workflow는 더 복잡해집니다. SDLC Client는 그 복잡성을 숨기는 대신, 안정적인 절차로 바꿔 제품 경험 안에 넣습니다.

Pi as the runtime

일하는 세션과
설명하는 세션을 분리합니다.

하나의 Pi session이 모든 일을 떠안지 않습니다. base session은 실제 SDLC 작업을 이어 가고, 그 문맥에서 fork한 presentation session은 결과를 사용자 화면으로 번역합니다.

  • 문맥 유지같은 case의 결정과 진행을 base session에서 이어갑니다.
  • 역할 분리presentation은 repository와 lifecycle을 수정하지 않습니다.
  • 안정적인 forkPi의 non-interactive 실행과 session fork를 기본 경로로 씁니다.
01 · BASEactive

판단하고, 만들고, 기록한다

pi --print --session-id <base-id>
  • 현재 stage skill 실행
  • case와 source 변경
  • 사용자 action 이어받기
fork same context
02 · PRESENTATIONread only

복잡한 결과를 쉽게 보여준다

  • 화이트보드용 구조화 JSON

SDLC skill system

기준을 세우고,
다음 단계를 골라 실행합니다.

세 이름은 같은 것이 아닙니다. SDLC가 전체 작업의 순서와 기록 방식을 정하고, orchestrator가 현재 상태에 맞는 진입점을 찾으면, 단계별 skill이 실제 작업과 산출물을 이어갑니다.

  1. 01 · STANDARD전체 기준
    SDLC

    작업의 순서와
    품질 기준을 정합니다.

    Plan부터 Documentation과 Done까지 하나의 lifecycle로 이어집니다. 보통 하나의 PR 범위를 case로 두고, 사람이 각 단계의 결정과 산출물을 확인하고 다듬습니다.

    • Plan → Design → Build → Verify → Documentation → Done
    • case에 단계별 입력과 결과를 축적
    • 요구사항과 최종 판단은 사람이 소유
    SDLC 문서에서 자세히 보기 ↗
  2. 02 · ENTRYPOINT다음 단계 선택
    sdlc-orchestrator

    현재 상태를 읽고
    알맞은 skill로 연결합니다.

    작업을 시작할 때 사용하는 표준 진입점입니다. 현재 case와 stage를 확인해 지금 필요한 단계를 고르므로, 사용자가 매번 실행 순서를 기억하지 않아도 됩니다.

    • 현재 lifecycle 상태 확인
    • 다음 단계의 skill 선택과 연결
    • Claude Code, Codex, Pi에서 같은 흐름 제공
    sdlc-orchestrator 문서에서 자세히 보기 ↗
  3. 03 · EXECUTION단계별 실행
    sdlc-*

    각 단계의 일을 하고
    다음 세션까지 남깁니다.

    sdlc-plan, sdlc-design처럼 단계마다 전용 skill이 실행됩니다. 결과는 .sdlc/**/* 아래 case와 artifact로 남아 새 세션에서도 이어서 작업할 수 있습니다.

    plandesignbuildverifydocumentation

티켓 또는 요청→ sdlc-orchestrator→ 현재 단계의 sdlc-*→ case와 산출물→ 다음 단계

$ cd tools/sdlc-client

# 2. 의존성과 로컬 환경 준비

$ ./bin/sdlc-client local setup

# 3. 준비 상태 확인
$ ./bin/sdlc-client local doctor

# 4. 시작

01SDLC Client는 Agent 채팅 UI인가요?

아닙니다. Agent의 전체 대화를 브라우저에 복제하는 대신, Jira 티켓과 SDLC case를 연결하고 현재 단계의 요약, 이해 자료, 선택지를 보여주는 작업 표면입니다.

02기존 SDLC와 무엇이 다른가요?

lifecycle 자체는 같습니다. plan → design → build → verify → documentation 규칙과 산출물 계약은 유지하고, Client가 worktree, case, session, 화면 표시를 제품 경험으로 조율합니다.

SDLC 문서에서 자세히 보기 ↗ sdlc-* 스킬 문서에서 자세히 보기 ↗
03왜 Jira 티켓 하나를 case 하나로 연결하나요?

사람이 기억해야 하는 매핑을 줄이고, 작업의 identity와 복원 경로를 안정적으로 만들기 위해서입니다. 기존 managed case가 있으면 새로 만들지 않고 이어서 사용합니다.

04sdlc-orchestrator는 무엇을 하나요?

lifecycle stage가 아니라 entrypoint입니다. case metadata를 읽어 현재 stage와 status를 복원하고, 그 단계에 맞는 sdlc-* skill로 라우팅합니다.

sdlc-orchestrator 문서에서 자세히 보기 ↗
05왜 Pi session을 두 개로 나누나요?

실제 작업과 사용자 설명의 책임이 다르기 때문입니다. base session은 판단과 파일 변경을 수행하고, fork한 presentation session은 같은 문맥을 읽어 화면용 JSON만 만듭니다.

06presentation session이 case를 바꿀 수 있나요?

아니요. repository 파일과 lifecycle metadata를 수정하지 않는 표시 전용 경계입니다. base 결과와 case 산출물을 쉬운 요약, 도식, action 후보로 변환합니다.

07Agent가 stage를 마음대로 넘길 수 있나요?

넘길 수 없습니다. 공식 상태는 metadata.yaml에 있고, prepare, checkpoint, finish, finalize 같은 core script가 전이를 관리합니다. 중요한 단계 전환에는 마무리 점검이 있습니다.

08사람이 결정하는 부분은 어디인가요?

문제 범위, 제품 방향, trade-off, 사람의 기능 확인처럼 의미 있는 선택은 사람이 소유합니다. Agent는 근거, 대안, 영향과 추천을 준비합니다.

09동시에 여러 요청을 보낼 수 있나요?

같은 case에 operation이 pending 또는 running이면 추가 action을 막습니다. 서버가 queue 상태를 소유하고 화면은 polling으로 대기, 실행, 완료 상태를 보여줍니다.

10Local mode와 remote mode의 차이는 무엇인가요?

기본 경로는 개인 개발 환경의 local mode입니다. remote mode는 OIDC 사용자 로그인과 service account 기반 Jira·GitHub·Pi 실행을 검증하는 Docker Compose PoC 경로입니다.

11Codex도 사용할 수 있나요?

비교와 rollback을 위한 adapter가 남아 있습니다. 다만 안정적인 non-interactive 실행과 session fork를 제공하는 Pi가 현재 기본 runtime입니다.

12다음으로 확장할 수 있는 것은 무엇인가요?

ticket–case 매핑 정책, 운영 audit, 실제 팀 사용 데이터에 기반한 work surface 품질, remote 운영 경계를 더 다듬을 수 있습니다. lifecycle 규칙은 유지하면서 제품 표면을 확장하는 방향입니다.
